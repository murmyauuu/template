# TripGo

Сервис поездок для курса «Разработка микросервисов на Go».
Текущая работа — лабораторная № 1: HTTP API и PostgreSQL.

## Состояние

Сервис создаёт, возвращает и завершает поездки, отвечает на `/health` и `/ready`.
Конфигурация читается из env, HTTP-типы и интерфейсы сгенерированы из контракта
курса. Две миграции создают таблицы поездок и историю статусов, репозитории
работают через `pgx` и `squirrel`. Создание и завершение записывают поездку
и историю в одной транзакции. Бонусные идемпотентность и Dockerfile ещё не добавлены.

## Требования

- Go 1.24 или новее;
- Docker с запущенным daemon;
- GNU Make;
- `tripgoctl` из [course-infra](https://github.com/course-go-autumn-2026/course-infra).

`tripgoctl` поддерживает Linux и macOS. На Windows команды окружения
выполняются в WSL. Go, Make и CLI должны быть доступны в терминале,
из которого запускается соответствующая команда.

## Окружение первой работы

В корне уже лежит `environment.toml` для лабораторной № 1.
Он включает только PostgreSQL.

В терминале Linux/macOS из корня проекта:

```sh
tripgoctl doctor
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
```

В WSL этот репозиторий доступен по пути `/mnt/d/template`.
Если CLI установлен в пользовательский каталог, добавьте его в PATH
текущего терминала:

```sh
export PATH="$HOME/.local/bin:$PATH"
cd /mnt/d/template
```

Во время работы оставляйте сеанс Ubuntu открытым: остановка WSL останавливает
его Docker daemon и локальный кластер. Если дистрибутив был остановлен,
после его запуска повторите `tripgoctl cluster start` и
`tripgoctl environment start`.

Адрес PostgreSQL берётся из `.env`, который создаёт `tripgoctl`.
Этот файл, каталог `.tripgo/` и собранные бинарники исключены из Git.
Makefile загружает `.env.example`, затем `.env`: локальные адреса из `tripgoctl`
заменяют значения примера. Настройки можно переопределить при вызове Make,
например `make run HTTP_ADDR=:8081`.

## Конфигурация

Приложение читает только переменные окружения. При прямом запуске бинарника
их нужно передать самостоятельно; файлы `.env` читает Makefile.
Все переменные из `.env.example` обязательны, таймауты должны быть положительными.

| Переменная | Назначение |
|---|---|
| `HTTP_ADDR` | Адрес сервера в формате `host:port` |
| `LOG_LEVEL` | Уровень логов `debug`, `info`, `warn` или `error` |
| `SHUTDOWN_TIMEOUT` | Общий бюджет остановки сервиса |
| `HTTP_READ_TIMEOUT` | Время чтения запроса |
| `HTTP_READ_HEADER_TIMEOUT` | Время чтения заголовков |
| `HTTP_WRITE_TIMEOUT` | Время записи ответа |
| `HTTP_IDLE_TIMEOUT` | Время ожидания следующего запроса на соединении |
| `DATABASE_URL` | URL подключения к PostgreSQL |
| `DATABASE_MAX_CONNS` | Максимальное число соединений, больше нуля |
| `DATABASE_MIN_CONNS` | Минимальное число соединений, от нуля до максимума |
| `DATABASE_MAX_CONN_LIFETIME` | Максимальное время жизни соединения |
| `DATABASE_CONNECT_TIMEOUT` | Таймаут подключения к БД |
| `DATABASE_QUERY_TIMEOUT` | Таймаут запроса к БД |

Продолжительности записываются с единицей измерения, например `5s` или `30m`.
При ошибке конфигурации возвращается имя переменной; пароль из URL в ошибку
не попадает.

## Генерация и сборка

`oapi-codegen` версии `v2.5.1` и `goose` версии `v3.24.1` закреплены в `go.mod`
как Go tools. Отдельная глобальная установка не нужна.

```sh
make generate
go build ./...
go vet ./...
make test
```

В `api/oapi-codegen.yaml` перечислены пять операций первой работы:
`createTrip`, `getTrip`, `finishTrip`, `health`, `ready`.
Результат лежит в `api/trip.gen.go`; этот файл не редактируется вручную.
Исходные файлы в `contracts/` скопированы из курса без изменений.
`make test` запускает `go test -race ./...`. Unit-тесты добавляются в работе 2;
для текущей работы ниже приведены проверки API через `curl`.

## Запуск

После `tripgoctl environment start` из корня проекта:

```sh
make migrate
make run
```

В другом терминале:

```sh
curl -i http://localhost:8080/health
curl -i http://localhost:8080/ready
```

Обе проверки возвращают `200` и `{"status":"ok"}`, когда БД доступна.
`/health` не обращается к PostgreSQL. `/ready` делает `Ping` с бюджетом
`DATABASE_QUERY_TIMEOUT`; при сбое возвращает `503` и `{"status":"unavailable"}`.
После восстановления БД готовность проверяется снова, перезапуск не требуется.

При старте выполняется отдельный `Ping` в пределах `DATABASE_CONNECT_TIMEOUT`.
Если подключение не удалось, сервис завершается с ошибкой до запуска HTTP.
Размер пула, время жизни и таймаут подключения берутся из env.

`SIGINT` (Ctrl+C) и `SIGTERM` запускают остановку: сервер прекращает принимать
соединения, дожидается текущих запросов, затем закрывает пул. На весь процесс
отведён `SHUTDOWN_TIMEOUT`. Если бюджет исчерпан, процесс пишет ошибку в лог
и завершается с ненулевым кодом. Логи выводятся в stdout в формате JSON.

`make build` создаёт бинарник `bin/trip-service`. При его прямом запуске
переменные окружения нужно передать самостоятельно.

## Миграции

```sh
make migrate
make migrate-status
```

`00001_create_trips.sql` создаёт поездки с ограничениями координат, цены,
статуса и времени завершения. Частичный уникальный индекс
`trips_active_driver_uniq` действует только для `status = 'active'`: конкурентные
вставки одному водителю дают одну поездку, остальные получают `23505`.
После завершения поездки водитель снова может получить активную поездку.

`00002_create_trip_status_history.sql` создаёт журнал статусов с внешним ключом
на поездку и `ON DELETE CASCADE`. Колонка `last_position_at` появится в работе 3.

`make migrate-down` откатывает одну последнюю миграцию. Для полного отката этих
двух миграций команду выполняют дважды: сначала удаляется история, затем поездки.
`make migrate` применяет их снова. Откат удаляет данные соответствующей таблицы.
Уже применённые SQL-файлы не редактируются; изменения схемы идут новыми миграциями.

## Проверка операций

При запущенном сервисе:

```sh
curl -i -X POST localhost:8080/api/v1/trips \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"5cb72c04-7650-45c9-a79b-bcdba0631e0c",
       "driver_id":"8860b315-ec86-42eb-a17c-7c163d721ff5",
       "start_point":{"latitude":59.9398,"longitude":30.3146},
       "end_point":{"latitude":59.9290,"longitude":30.3626},"price":1450}'
```

Ожидаются `201`, полная поездка и заголовок `Location`. Скопируйте `id` из ответа:

```sh
TRIP_ID='<id из ответа>'
curl -i "localhost:8080/api/v1/trips/$TRIP_ID"
curl -i -X POST "localhost:8080/api/v1/trips/$TRIP_ID/finish"
curl -i -X POST "localhost:8080/api/v1/trips/$TRIP_ID/finish"
```

Чтение и первое завершение возвращают `200`, повторное завершение — `409`
с `code = trip_completed`. До завершения повторное создание тому же водителю
возвращает `409 driver_busy`; после завершения можно создать следующую поездку.
Случайный отсутствующий UUID даёт `404 trip_not_found`, некорректное тело или
UUID — `400 invalid_request`. Ошибки имеют тип `application/problem+json`.

В JSON создания обязательны ровно пять полей, а в каждой точке — `latitude`
и `longitude`. Отсутствующие поля, `null`, лишние поля и неверный регистр имён
отклоняются. Нулевые UUID пользователя и водителя запрещены, координаты ограничены диапазонами
`[-90, 90]` и `[-180, 180]`, цена — неотрицательный `int64` в рублях.
Размер тела ограничен 64 КиБ, `Content-Type` — `application/json` с допустимыми
параметрами. У завершения тело пустое. Заголовок `Idempotency-Key` пока не используется.

## Решения

Менеджер транзакций находится в `internal/database/transaction.go`.
`Do(ctx, fn)` открывает транзакцию и передаёт её в callback через приватный ключ
контекста. `ExecutorFromContext(ctx, pool)` возвращает эту транзакцию, если она
есть, или пул для вызова вне `Do`. Это позволяет репозиторию получать исполнителя
без аргумента `pgx.Tx` в своих методах.

Бизнес-операции находятся в `internal/trip/service.go` и используют интерфейс
`TxManager` с единственным методом `Do`. Создание внутри callback добавляет
поездку и переход `NULL → active`, завершение — обновление и переход
`active → completed`. Ошибка второй записи отменяет первую. UUID и время
генерирует сервис; время округляется до микросекунд, которые хранит PostgreSQL.

Если callback возвращает `nil`, менеджер делает commit. Ошибка возвращается
вызывающему коду, а отложенный rollback отменяет изменения. При панике этот же
rollback выполняется при раскрутке стека, после чего исходная паника идёт дальше.
После успешного commit повторный rollback возвращает `pgx.ErrTxClosed`, который
можно игнорировать. Другие ошибки rollback объединяются с исходной ошибкой;
ошибка commit также возвращается наружу.

Вложенный `Do` передаёт callback текущий контекст: новые транзакция, соединение
и savepoint не создаются. Commit и rollback выполняет внешний вызов.
Ошибку вложенного callback нужно вернуть из внешнего callback, чтобы отменить
всю операцию.

На транзакцию вместе с callback и commit отводится `DATABASE_QUERY_TIMEOUT`.
Для rollback создаётся отдельный контекст через `context.WithoutCancel` с тем же
таймаутом: отмена запроса не должна мешать очистке соединения.

Изоляция задаётся явно при `BeginTx`: `READ COMMITTED`. Она подходит для коротких
операций этого сервиса. Запрет двух активных поездок держит уникальный индекс,
поэтому корректность создания не зависит от предварительного чтения состояния
водителя.

Запросы репозиториев собирает `squirrel` с плейсхолдерами `$N`. Значения передаются
отдельно от SQL. В `driver_busy` превращается только ошибка `23505` индекса
`trips_active_driver_uniq`; нарушение других ограничений остаётся внутренней ошибкой.
Вызовы репозиториев ограничены `DATABASE_QUERY_TIMEOUT` и сохраняют контекст
транзакции. Время из PostgreSQL приводится к UTC, `last_position_at` пока равно `null`.

Репозиторий завершает поездку условным `UPDATE ... WHERE status = 'active'`
с `RETURNING`. Если два запроса приходят одновременно, PostgreSQL блокирует строку
на время первого обновления. После его commit второй запрос повторно проверяет
условие и не обновляет завершённую поездку. Дополнительное чтение различает
отсутствующую и уже завершённую поездки. Без условия второй запрос мог бы
перезаписать `finished_at` и добавить лишнюю запись истории.

## Структура

```text
cmd/trip-service/    точка входа приложения
internal/           код сервиса
api/                сгенерированные HTTP-типы и интерфейсы
contracts/          неизменённые контракты курса
migrations/         SQL-миграции goose
deploy/             файлы контейнерного запуска
docs/               план и проверки
```

Все работы выполняются в одном репозитории. Лабораторная № 1 ведётся
в ветке `homework/01`; PR направляется в `main` и остаётся открытым до проверки.
